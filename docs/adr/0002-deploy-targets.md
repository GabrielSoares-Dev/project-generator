# Deploy Targets: serverless cloud by default, AWS or GCP via Terraform

Derived Projects start as personal projects but must be able to grow into SaaS products or client work, so the Deploy Target is chosen per Derived Project, like its stack. Both AWS and GCP are supported, each through its own recipe in the Template. The default is serverless (Cloud Run or Lambda): with little traffic the free tiers make it near-zero cost, and there is no server to patch or secure. A VPS was the original default, but it only existed because the agent was going to run there; once Autonomous Runs moved to Claude Code cloud sessions (ADR-0005), keeping a VPS just for hosting was not worth maintaining. All cloud infrastructure is defined with Terraform/OpenTofu, because an agent working unattended cannot click through consoles, and infrastructure that lives outside the repo becomes knowledge only one person holds.

## Considered Options

- **VPS with Docker Compose as the default**: rejected after ADR-0005; a fixed monthly cost and a server to maintain, where serverless free tiers cost nothing at personal-project traffic.
- **AWS only**: rejected; client work may demand GCP. Recipes (ADR-0001) keep the cost of supporting both low.
- **CDK / Serverless Framework**: rejected; AWS-only, while Terraform covers both clouds with one tool.

## Consequences

- The cloud runtime model (functions or containers) is also decided per Derived Project, and the choice is recorded in that project's ADRs.
- Application code is always a plain HTTP server with no platform-specific code (no Lambda handlers, no Cloud Functions entry points). Adapting it to a function runtime happens only in the deploy layer (image, Lambda Web Adapter, Terraform), so switching between container and function is configuration, never a rewrite. This is the reason the backend follows clean architecture: the platform is an outer detail the core never sees.
- **Exception for Event Functions** (non-HTTP functions triggered by an event or schedule): they cannot be a plain HTTP server, so each one gets a thin platform adapter in `infra/functions/<name>/`, one file per platform (Lambda, GCP), which converts the event into the use case's input DTO and calls `execute()`. The use case never knows where the event came from, and switching clouds means swapping that adapter. HTTP APIs still never contain platform code. An Event Function that uses the project's domain lives inside the backend repository, beside `infra/http/`; one independent of the domain (e.g. resizing images) gets its own repository.
- The decision guide must cover cloud choice, runtime model (including the Java cold-start cost on functions) and database engine, which is also chosen per Derived Project from PostgreSQL, MySQL or the cloud's native NoSQL (DynamoDB on AWS, Firestore on GCP).
- Choosing a native NoSQL ties that Derived Project's persistence adapters to its cloud: moving clouds means rewriting the repository implementations in `infra`, while domain and application stay untouched behind their ports. Integration tests use the local emulators (DynamoDB Local, Firestore emulator) in containers.
- Besides production, Terraform creates a **dev set of mechanism resources** (`-dev` buckets, queues, topics; email in sandbox mode) used only by developers' machines during Local Review, so code under review never touches production resources. It is not a staging environment: no app or database is deployed there.
- **Exception for PHP, Node and Go on AWS**: Bref is built around the Serverless Framework (its plugin and documentation target it), and the user already masters the Serverless Framework for PHP and Node (Go follows for consistency), so in PHP, Node and Go projects on AWS the **Serverless Framework** (with Bref for PHP) packages and manages the Lambda functions and the API Gateway, while **Terraform manages everything else** (database, buckets, CDN, alerts, budget, `-dev` resources); the two exchange identifiers through SSM parameters. `serverless deploy` runs only in the pipeline, authenticated through OIDC (ADR-0010). Serverless Framework v4 requires a login and a license, free for individuals and organizations under US$ 2M yearly revenue. PHP, Node and Go on GCP, and Java everywhere, use Terraform only.
- **Exception for Node and Go HTTP APIs on Lambda**: instead of the Lambda Web Adapter, a single entry-point file wraps the app (`infra/functions/api/LambdaHandler.ts` with `@fastify/aws-lambda` in Node; `internal/infra/functions/api/lambda_handler.go` with `aws-lambda-go-api-proxy` in Go), the user's preferred approach, as with `@vendia/serverless-express` in their boilerplate. It is the only platform-specific file of the API; `domain`, `application` and the rest of `infra` stay untouched, and containers start the same app through the plain server entry point.
- Frontends (SPAs) are static files served from the project's own cloud through a CDN: S3 + CloudFront on AWS, Cloud Storage + Cloud CDN on GCP, defined in the same Terraform as the backend. A frontend that turns on SSR becomes a server and follows the backend's runtime model instead.
- Relational databases default to external managed services with free tiers (Neon for PostgreSQL, TiDB Serverless for MySQL), so a personal project costs nothing; the recipe migrates to RDS or Cloud SQL when the project becomes a product or a client requires it. Free-tier terms are to be re-checked when the recipes are written.
