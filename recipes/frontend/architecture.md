# Frontend architecture

The folder structure and rules every frontend Stack Recipe follows, for React and Angular alike. Visual components follow **Atomic Design**; data, state and API access live in their own folders beside it, because Atomic Design only organizes the UI.

The frontend is a single-page app that calls its backend directly through a configurable API URL; there is no BFF by default (ADR-0007). When a project needs server-side rendering, React switches React Router to framework mode and Angular adds `@angular/ssr`; the folder structure below stays the same, and the repository gains the two-target `Dockerfile` (`dev` / `prod`) described in `recipes/backend/clean-architecture.md`.

Frontend repositories have **no dev container** (too heavy for the gain): they run on the host with Node and pnpm, versions pinned in the repository (`.nvmrc` / `engines`, and `packageManager` for pnpm via Corepack) so the machine, CI and cloud sessions still match.

## Folder structure

```
src/
├── app/                        routes, providers, bootstrap
├── components/
│   ├── atoms/                  smallest elements: design-system components (shadcn/ui, spartan/ui or Angular Material) plus your own
│   ├── molecules/              a few atoms with one simple job: search field, list item
│   ├── organisms/              complete sections: header, roles table, role form
│   └── templates/              page layouts, no real data
├── pages/                      a template filled with real data, one per route
├── services/<feature>/         backend calls and types for a feature, generated by orval from the backend's OpenAPI spec (ADR-0008); never hand-written
├── state/<feature>/            React: hooks/stores. Angular: services with signals
└── shared/
    ├── http/                   base HTTP client (API URL, cookies, Problem Details errors handled by `code`, ADR-0011)
    ├── utils/                  generic helpers (input masks, small pure functions); no display formatting: the backend sends formatted values
    ├── types/                  generic types (pagination, Problem Details errors)
    ├── constants/              routes, keys, limits
    └── hooks/                  React: reusable hooks with no business logic. Angular: generic pipes and directives
```

The design system's CLI is configured to generate its components directly into `components/atoms/` (for shadcn/ui, the `ui` alias in `components.json`), so updates keep working without moving files.

## Conventions

- **Formatting**: one explicit `.prettierrc`, the same in both frameworks, checked in CI and applied on pre-commit: `{ "semi": true, "singleQuote": true, "trailingComma": "es5", "arrowParens": "avoid", "bracketSpacing": true, "bracketSameLine": true, "printWidth": 80, "tabWidth": 2, "useTabs": false, "endOfLine": "auto" }`, plus an `.editorconfig` (UTF-8, 2-space indent, final newline, trimmed trailing whitespace). No third-party preset.
- **File and folder names**, each framework in its own idiom, checked by lint (eslint-plugin-check-file):
  - **React**: components in a PascalCase folder with `index.tsx` (`components/atoms/Button/index.tsx`); hooks named `useSomething`; other files kebab-case (`input-mask.ts`).
  - **Angular**: the official style guide, kebab-case with a type suffix (`button.component.ts`, `auth.service.ts`, `private.guard.ts`).
- **Imports** use path aliases mirroring the architecture folders (`@components/*`, `@pages/*`, `@services/*`, `@state/*`, `@shared/*`). A component's own `index.tsx` is its entry point, but there are **no aggregated barrels** (`components/index.ts` re-exporting everything): they hide dependencies from dependency-cruiser, create import cycles and hurt tree-shaking.
- **Strictness**, the same in both frameworks and failing CI:
  - TypeScript: `strict` plus `noImplicitReturns`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature`, `noFallthroughCasesInSwitch`, `noUnusedLocals`, `noUnusedParameters`; Angular also `strictTemplates`, `strictInjectionParameters`, `strictInputAccessModifiers`.
  - ESLint with `--max-warnings 0`, `no-unused-vars` on, `@typescript-eslint/naming-convention` (camelCase variables and functions, PascalCase types and components, `use` prefix for hooks, `UPPER_SNAKE_CASE` constants) and import ordering (simple-import-sort).
- **Code style**: named exports only (no `export default`, except config files); `type` for props and types, `interface` only where the framework requires it; user-facing text in the product's language (chosen per project), everything else in English. Angular: standalone components, signals for state, functional guards and interceptors, `inject()` instead of constructor injection.
- **Tests sit next to the code they test**, with the `.spec` suffix in both frameworks (`Button/index.spec.tsx`, `button.component.spec.ts`).

There is **no use-case layer** in the frontend: business rules live in the backend and the API client is generated, so a use case would only forward calls. Screen logic (combining calls, view rules) lives in the feature's `state/`.

## Rules

Every rule is checked by the architecture-validation gate (`recipes/quality-gates.md`).

1. **Visual hierarchy**: each level of `components/` imports only from the levels below it. Atoms import nothing from `components/`; molecules use atoms; organisms use molecules and atoms; templates use organisms, molecules and atoms.
2. **Atoms, molecules and templates are purely visual**: no business state, no API calls. They receive data through props/inputs.
3. **Only `organisms` and `pages` use `state/`**: that is where the UI meets data.
4. **`state/` uses `services/`, and `services/` uses `shared/http`**: components never call the API directly.
5. **`shared/` imports nothing from the rest of the app**: it sits at the bottom, and every other folder may use it.

## Configuration

Configuration (API URL and other public values) is fixed at build time: `VITE_*` variables in React, `environment.ts` in Angular. With production as the only environment, one build per environment costs nothing. If a project adds a staging environment, the recipe switches to a runtime `config.json` loaded at startup, so a single build serves every environment.

## Performance

- Every page is **lazy-loaded** per route, so the first load carries only what it needs.
- **Bundle size is a Quality Gate**: Angular budgets and size-limit in React, both at 500 KB warning / 1 MB error for the initial bundle (the values of the user's Angular boilerplate).
- Images in WebP / AVIF with `loading="lazy"`.

## Responsiveness and theme

- **Mobile-first is mandatory**: every screen works from phone to desktop.
- **Dark mode is optional per project**, decided with the Brand Tokens in `/new-project`.

## Screen states

Every screen that loads data handles three states with three standard organisms, checked by `/code-review`:

- **Loading**: a skeleton shaped like the content, not a centred spinner.
- **Empty**: the message and action sent by the backend (`title`, `description`, semantic content fields).
- **Error**: the Problem Details `detail`, the `traceId` (to find the logs) and a "try again" button.

## Error reporting

A global handler (React `ErrorBoundary` plus `window` error and unhandled-rejection listeners; Angular `ErrorHandler`) sends every uncaught error to the backend at `POST /v1/client-errors`, which logs it like any other error, so frontend failures appear in the same cloud logs and trigger the same alerts. Source maps are uploaded at deploy so logged stack traces point to the original code. No third-party error tracker. Real-user monitoring (CloudWatch RUM / Firebase Performance) is an on-demand mechanism for when frontend performance becomes a concern.

## Visual identity

Every screen follows the Derived Project's Brand Tokens (colors, typography, radii), set when the project is created and applied through the design system's theme. A ticket may attach a screenshot or sketch when a screen needs something specific.

## Tests

- **Unit and component tests** with Testing Library, the API mocked with **MSW**. They play the integration-test role on the frontend side, without coupling CI to the backend repository.
- **Coverage ≥ 80%**, excluding the design-system components generated into `components/atoms/` and configuration files.
- **End-to-end tests** (Playwright) are optional, added when a project matures.
- **Test structure** (also for mobile), adapting the backend's testing rules:
  - `// given`, `// when`, `// then` blocks, one behaviour per test, names "should … when …";
  - **mocks only at the edges**: the API through MSW (with the orval-generated mocks) and, on mobile, native modules; never the app's own components or `state/`;
  - **test data builders** in a shared test helpers folder;
  - **test what the user sees**: Testing Library queries by text and accessible role, never by CSS class or internal id.
