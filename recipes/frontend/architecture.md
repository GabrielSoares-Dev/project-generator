# Frontend architecture

The folder structure and rules every frontend Stack Recipe follows, for React and Angular alike. Visual components follow **Atomic Design**; data, state and API access live in their own folders beside it, because Atomic Design only organizes the UI.

The frontend is a single-page app that calls its backend directly through a configurable API URL; there is no BFF by default (ADR-0007). When a project needs server-side rendering, React switches React Router to framework mode and Angular adds `@angular/ssr`; the folder structure below stays the same, and the repository gains the two-target `Dockerfile` (`dev` / `prod`) described in `recipes/backend/clean-architecture.md`.

Web frontend repositories ship a **dev container** built, like a backend's, on a `Dockerfile` (`dev` target on the Node image of the pinned major) and a `docker-compose.yml` service, with `node_modules` in a Docker volume and a polling file watcher so edits made on a Windows or macOS host reach Vite, so the only requirement on the machine is Docker (`recipes/frontend/react.md`, Dev container). Running on the host with Node and pnpm stays supported; versions are pinned in the repository either way (`.nvmrc` / `engines`, and `packageManager` for pnpm via Corepack) so the machine, CI and cloud sessions match.

## Folder structure

```
src/
├── main.tsx                    bootstrap: renders the providers and the router
├── providers.tsx               the app's providers (query client, color scheme); router.tsx holds the routes
├── types/                      the types of the files directly in src/ (providers props)
├── components/
│   ├── atoms/                  smallest elements: design-system components (shadcn/ui, spartan/ui or Angular Material) plus your own
│   ├── molecules/              a few atoms with one simple job: search field, list item
│   ├── organisms/              complete sections: header, roles table, role form
│   └── templates/              page layouts, no real data
├── pages/                      a template filled with real data, one per route
├── services/<feature>/         one plain call function per endpoint (that only calls the endpoint through `shared/http`), plus Zod schemas, MSW mocks and a single generated `<title>.schemas.ts` with the types, generated by orval from the backend's OpenAPI spec (ADR-0008); never hand-written, with no `model/` folder, no barrel files and no TanStack Query hooks
├── state/<feature>/            client state shared across screens, only when a project needs it (React: Zustand stores; Angular: services with signals); absent by default
└── shared/
    ├── http/                   base HTTP client (API URL, cookies, Problem Details errors handled by `code`, ADR-0011)
    ├── utils/                  generic helpers (input masks, small pure functions); no display formatting: the backend sends formatted values
    ├── types/                  generic types (pagination, Problem Details errors)
    ├── constants/              routes, keys, limits
    └── hooks/                  React: reusable hooks with no business logic. Angular: generic pipes and directives
```

Two kinds of folder repeat inside the folders above, wherever the code needs them:

- **`types/`**: every type, props, view model or helper type has its file here, next to the code that uses it (`health-panel/types/health-panel-view.ts`, `types/app-providers-props.ts` for `src/providers.tsx`, `state/<feature>/types/…`). A type is **never declared inside a component, hook, page or provider file** (an ESLint rule bans `type` and `interface` declarations and object type literals outside `types/` and `*.d.ts`). `shared/types/` holds the generic ones.
- **Screens are split into sections.** A page never holds the markup of a section: it composes a template and a list of sections, each section an organism in its own component folder (`home` composes `app-layout` and `health-panel`), and a section that grows is split again into molecules. Every section owns its types.
- **Components are dumb; only pages have data hooks.** Atoms, molecules, organisms and templates receive everything through props and call no API (the textbook Atomic Design: "a page is a template filled with real data"). The data and the screen's logic live in the page's own `hooks/` folder (`pages/home/hooks/useHome.ts`): TanStack Query is used there, over the call functions of `services/` (the hook owns the query key, the `queryFn` and the error handling), and the hook returns a **view model** for the page, whose parts are the props of its sections (`HomeView.healthPanel`, a discriminated union such as `loading | error | ready`, each case carrying the props of the component to render). The page passes each part to its section, and the section only switches on it. A hook is never shared by two pages, and a page splits its hook into small private functions before it grows past the 30-line limit that applies to every function.
- **Very small UI-only logic stays in the component**: a component function has at most **5 statements** (ESLint `max-statements`), so one `useState` for an open/closed menu and a one-line handler fit, and anything more (fetching, deciding what to show, building messages) moves to the page's hook.

The design system's CLI is configured to generate its components into `components/atoms/` (for shadcn/ui, the `ui` alias in `components.json`) and the result is then reorganised to the naming rules below. Atoms are linted like any other code; only coverage excludes them, since the design system owns their behaviour.

## Conventions

- **Formatting**: one explicit `.prettierrc`, the same in both frameworks, checked in CI and applied on pre-commit: `{ "semi": true, "singleQuote": true, "trailingComma": "es5", "arrowParens": "avoid", "bracketSpacing": true, "bracketSameLine": true, "printWidth": 80, "tabWidth": 2, "useTabs": false, "endOfLine": "auto" }`, plus an `.editorconfig` (UTF-8, 2-space indent, final newline, trimmed trailing whitespace). No third-party preset.
- **File and folder names**, each framework in its own idiom, checked by lint (eslint-plugin-check-file):
  - **React**: every component, organism, template and page lives in a **kebab-case folder named after it** (`health-panel`, `app-layout`, `home`; a page is named after its screen **without a `page` suffix**, so `home`, `invoices`, `login`, and its component is `Home`) and its entry file is `index.tsx`, so the folder name says what it is and every entry file is called `index.tsx`; its test sits in the same folder and is **named after the folder** (`health-panel/health-panel.spec.tsx`, never `index.spec.tsx`), so open tabs tell the component and its test apart. **One component per file, design-system components included**: the CLI of shadcn/ui writes several components into one file (`card.tsx` holds Card, CardHeader, CardTitle…), so after generating them each is split into its own folder (`atoms/card`, `atoms/card-header`, `atoms/card-title`), keeping only the parts the project uses. Hooks are named `useSomething` (`useHealthPanel.ts`); other files are kebab-case (`input-mask.ts`).
  - **Angular**: the official style guide, kebab-case with a type suffix (`button.component.ts`, `auth.service.ts`, `private.guard.ts`).
- **Imports** use path aliases mirroring the architecture folders (`@components/*`, `@pages/*`, `@services/*`, `@state/*`, `@shared/*`). A component's own `index.tsx` is its entry point, but there are **no aggregated barrels** (`components/index.ts` re-exporting everything): they hide dependencies from dependency-cruiser, create import cycles and hurt tree-shaking.
- **Strictness**, the same in both frameworks and failing CI:
  - TypeScript: `strict` plus `noImplicitReturns`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature`, `noFallthroughCasesInSwitch`, `noUnusedLocals`, `noUnusedParameters`; Angular also `strictTemplates`, `strictInjectionParameters`, `strictInputAccessModifiers`.
  - ESLint with `--max-warnings 0`, `no-unused-vars` on, `@typescript-eslint/naming-convention` (camelCase variables and functions, PascalCase types and components, `use` prefix for hooks, `UPPER_SNAKE_CASE` constants) and import ordering (simple-import-sort).
- **Code style**: named exports only (no `export default`, except config files); `type` for props and types, declared in `types/` folders, `interface` only where the framework requires it; user-facing text in the product's language (chosen per project), everything else in English. Angular: standalone components, signals for state, functional guards and interceptors, `inject()` instead of constructor injection.
- **Tests sit next to the code they test**, with the `.spec` suffix in both frameworks, named after the component (`health-panel/health-panel.spec.tsx`, `button.component.spec.ts`). Component tests (`.spec.tsx`, DOM and the API mocked with MSW) are the frontend's integration tests and run with `project test:integration`; the other `.spec.ts` files are unit tests (`project test:unit`).

There is **no use-case layer** in the frontend: business rules live in the backend and the API client is generated, so a use case would only forward calls. Screen logic (combining calls, view rules) lives in the screen's own `hooks/` folder; `state/` holds only client state shared across screens, and only when a project needs it.

## Rules

Every rule is checked by the architecture-validation gate (`recipes/quality-gates.md`).

1. **Visual hierarchy**: each level of `components/` imports only from the levels below it. Atoms import nothing from `components/`; molecules use atoms; organisms use molecules and atoms; templates use organisms, molecules and atoms.
2. **Atoms, molecules and templates are purely visual**: no business state, no API calls. They receive data through props/inputs.
3. **Only the `hooks/` folders of `pages` use `services/` and `state/`**: that is where the UI meets data; components never do.
4. **Only `services/` uses `shared/http`**: components and hooks never call the API directly, only through the call functions.
5. **`shared/` imports nothing from the rest of the app**: it sits at the bottom, and every other folder may use it.

## Configuration

Configuration (API URL and other public values) is fixed at build time: `VITE_*` variables in React, `environment.ts` in Angular. With production as the only environment, one build per environment costs nothing. If a project adds a staging environment, the recipe switches to a runtime `config.json` loaded at startup, so a single build serves every environment.

## Performance

- Every page is **lazy-loaded** per route, so the first load carries only what it needs.
- **Bundle size is a Quality Gate**: Angular budgets (500 KB warning / 1 MB error, the values of the user's Angular boilerplate) and size-limit in React, which has a single limit and so enforces the 1 MB error only.
- Images in WebP / AVIF with `loading="lazy"`.

## Responsiveness and theme

- **Mobile-first is mandatory**: every screen works from phone to desktop.
- **Dark mode is optional per project**, decided with the Brand Tokens in `/new-project`.

## Screen states

Every screen that loads data handles three states with three standard organisms, checked by `/code-review`:

- **Loading**: a skeleton shaped like the content, not a centred spinner.
- **Empty**: the message and action sent by the backend (`title`, `description`, semantic content fields).
- **Error**: the Problem Details `detail`, the `traceId` (to find the logs) and a "try again" button.

## Error reporting

A global handler (React `ErrorBoundary` plus `window` error and unhandled-rejection listeners; Angular `ErrorHandler`) sends every uncaught error to the backend at `POST /v1/client-errors`, which logs it like any other error, so frontend failures appear in the same cloud logs and trigger the same alerts. Source maps are uploaded at deploy so logged stack traces point to the original code. No third-party error tracker. Real-user monitoring (CloudWatch RUM / Firebase Performance) is an on-demand mechanism for when frontend performance becomes a concern.

## Visual identity

Every screen follows the Derived Project's Brand Tokens (colors, typography, radii), set when the project is created and applied through the design system's theme. A ticket may attach a screenshot or sketch when a screen needs something specific.

## Tests

- **Unit and component tests** with Testing Library, the API mocked with **MSW**. They play the integration-test role on the frontend side, without coupling CI to the backend repository.
- **Coverage ≥ 80%**, excluding the design-system components generated into `components/atoms/` and configuration files.
- **End-to-end tests** (Playwright) are optional, added when a project matures.
- **Test structure** (also for mobile), adapting the backend's testing rules:
  - given, when and then blocks separated by one blank line and without comments, one behaviour per test, names "should … when …";
  - **mocks only at the edges**: the API through MSW (with the orval-generated mocks) and, on mobile, native modules; never the app's own components, hooks or `state/`;
  - **test data builders** in a shared test helpers folder;
  - **test what the user sees**: Testing Library queries by text and accessible role, never by CSS class or internal id.
