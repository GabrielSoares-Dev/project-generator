# Autonomous Runs

How an Autonomous Run works in a Derived Project's repository (ADR-0005): started from the Claude mobile app (Code tab), runs in a Claude Code cloud session, only opens pull requests; the human always merges. This content is written into each generated repository's `AGENTS.md` and docs.

## Triggering

Two standard prompts:

- **`Implement issue #42`**: a specific ticket.
- **`Implement the next ready ticket`**: the agent picks the first open ticket labelled `ready-for-agent` whose blockers are all closed, in list order.

Both run Matt Pocock's `/implement`, which drives `/tdd`, runs the Quality Gates and `/code-review` before opening the pull request.

## Cloud environment

Each repository carries `scripts/agent-setup.sh`, set as the cloud environment's setup script and generated by `/new-project`. It installs the same pinned versions as the project (Java/Maven or Node/pnpm), the Quality Gate tools and Lefthook, and starts the database from `docker-compose` for integration tests, so the cloud session matches the developer's machine and CI.

## One ticket per session, several at once

Each ticket gets a fresh session and its own pull request (a clean context per ticket, small squash-merged pull requests). Several tickets can be worked at once in two ways, always one pull request per ticket:

- **Several sessions in parallel**, each started with `Implement issue #N`.
- **`Implement all ready tickets`**: one coordinating session lists the open `ready-for-agent` tickets whose blockers are closed and starts **one subagent per ticket in parallel**, each in its own git worktree and branch, each running `/implement` and opening its own pull request. The coordinator ends with a summary of what was opened and what got stuck. At most **3 subagents** run at once (configurable in `AGENTS.md`), to keep within the Pro plan's limits.

A ticket blocked by another starts only after the blocker is merged, and merging is human, so tickets unblocked by today's merges are picked up by the next run.

## Agent-ready tickets

`/to-tickets` writes every ticket in this shape, in English. A ticket gets the `ready-for-agent` label only when it has acceptance criteria.

- **Context**: why, with a link to the spec.
- **Acceptance criteria**, verifiable, as given / when / then. They become the `/tdd` tests.
- **Contract changes**: new or changed endpoints and their fields.
- **UI** (frontend tickets): the screen, with an optional screenshot or sketch.
- **Out of scope**: what not to do.
- **Blocked by**: the tickets it depends on.
- **Feature flag** (with its trial period) and **idempotency key**, when they apply.

## Pull request contents

Every agent pull request follows Matt Pocock's `/pr` skill, in English, plus:

- `Closes #<ticket>`, so the ticket closes on merge;
- the Quality Gates result;
- the `/code-review` summary (Standards and Spec);
- **step-by-step Local Review instructions**: the commands to run (including `seed:dev`, updated in the same pull request when entities change) and what to click to see the feature working;
- any decision the agent took that the human must confirm.

## When the agent is stuck

The agent never guesses. When a ticket is ambiguous or it gets stuck, it comments on the issue with its exact questions, switches the label to `needs-info`, opens a **draft** pull request if it has partial work, and ends the run. The human answers, sets the label back to `ready-for-agent` and starts a new run.

## Whole specs

Matt Pocock's `/implement-spec` remains available when the human prefers one integration-branch pull request for a whole spec.
