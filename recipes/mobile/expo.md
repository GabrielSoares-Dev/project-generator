# Expo

The mobile app Stack Recipe, in its first proven form: **a standalone app with no backend** (data on the device), generated end to end with every gate passing (Somaí, 2026-10-24). It follows `recipes/mobile/architecture.md`, `recipes/frontend/architecture.md` and `recipes/coding-standards.md`; this file is how to **generate** the repository so that every Quality Gate passes. Learned from generating one and running it through the gates.

A mobile app **with a backend** follows the same steps and adds what `recipes/mobile/architecture.md` describes (orval client in `services/`, axios in `shared/http`, TanStack Query in the page hooks, `openapi:check` as a real gate). That variant is not proven yet.

## What this recipe does not prove

- **Nothing was run on a phone, an emulator or a simulator.** The proof is typecheck, tests, the architecture gate and `expo export`, which runs Metro and Hermes over the whole app (it catches resolution and NativeWind transform errors). A first run on a device is a manual step for the user.
- **Maestro, EAS Build, EAS Submit and the store workflows** (`recipes/mobile/architecture.md`) are not generated, except `expo-dev-client`, an `eas.json` with a `development` Android profile and a manual `build-dev.yml` that calls the shared workflow `expo-eas-build` (it needs the `EXPO_TOKEN` secret and `eas init` from the user): the rest needs the user's Expo, Apple and Google accounts. The ADR of the deploy says so.
- **OCR** (reading the price from the camera) is a product decision, not a stack one: the project is generated with the camera preview and permission only.

## Generating the project

1. **Tooling**: Node on the latest LTS (`.nvmrc`, `engines`) and pnpm pinned in `packageManager`. With Corepack unable to prepare the pinned pnpm, `npm install pnpm@<version>` in a folder outside the project and put its `.bin` on the `PATH`. A Node LTS the machine lacks can be installed the same way (`npm install node@<version>`).
2. **Start from the official skeleton, then strip it**: `npx create-expo-app@latest <slug> --template blank-typescript --no-install`, then delete what it brings and the project does not want: its `.git`, `.claude`, `AGENTS.md`, `LICENSE`, `App.tsx`, `index.ts`. Write `package.json` by hand (`"main": "expo-router/entry"`, `packageManager`, `engines`) and `git init` **before the first install** (Lefthook's install script needs a repository).
3. **Versions**: the latest Expo SDK and the React and React Native it pins. `npx expo install` asks `api.expo.dev`, which a restricted network may block: take each Expo-managed package's version from `node_modules/expo/bundledNativeModules.json` and `pnpm add` it. A package missing from that file (`react-native-mmkv`, `react-native-nitro-modules`, `zustand`) takes the latest release that passes strict peers. Strip every `^` from `package.json` afterwards.
4. **pnpm settings** live in `pnpm-workspace.yaml`:
   - `strictPeerDependencies: true`, so a conflict fails at install time. A failed `pnpm add` **saves nothing to `package.json`**: repeat the whole command.
   - `allowBuilds`: `lefthook: true`, and `false` for `@parcel/watcher` and `unrs-resolver`, the dependencies that otherwise stop the install with `ERR_PNPM_IGNORED_BUILDS` (they ship prebuilt binaries).
   - `peerDependencyRules.allowedVersions` with `eslint-plugin-react-native-a11y>eslint: '9'`: the plugin declares ESLint up to 8 and works on 9 (rules only, no flat config of its own).
   - pnpm 12 adds `minimumReleaseAgeExclude` entries for fresh Expo releases by itself; keep them.
5. **Peer conflicts found on the first run**, each resolved by the newest version the stack supports:
   - `react-dom` is required by `@expo/metro-runtime`; install it at **exactly the React version** the SDK pins (the latest `react-dom` wants a newer React).
   - `@testing-library/react-native` 14 needs `test-renderer`, **not** `react-test-renderer`; its `render`, `fireEvent` and `renderHook` are asynchronous (`await render(...)`).
   - `react-native-css-interop` must be a **direct dependency** at the exact version NativeWind depends on, because pnpm does not expose it to the app and Metro fails with `Unable to resolve "react-native-css-interop/jsx-runtime"`.
   - TypeScript stays on the version Expo's template pins (6.0) while `latest` is 7; ESLint stays on 9 (`typescript-eslint` and the React plugins); NativeWind stays on **4.x with Tailwind 3.4** (NativeWind 5 is a release candidate for Tailwind 4).
6. **TypeScript**: `expo/tsconfig.base` plus the strict flags of `recipes/frontend/architecture.md`, the `paths` of the architecture folders (`./src/…`, no `baseUrl`), `"types": ["jest"]` (TypeScript 6 no longer includes `@types/*` on its own) and a `nativewind-env.d.ts` with `/// <reference types="nativewind/types" />` and `declare module '*.css';` (TypeScript 6 rejects an unresolved side-effect import such as `import '../global.css'`).
7. **Styling**: `babel.config.js` with `['babel-preset-expo', { jsxImportSource: 'nativewind' }]` and `'nativewind/babel'`; `metro.config.js` with `withNativeWind(getDefaultConfig(__dirname), { input: './global.css' })`; `tailwind.config.js` with the NativeWind preset, `darkMode: 'class'` and the colors as `hsl(var(--token))`; `global.css` with the three Tailwind directives, the tokens in `:root` and the dark set in `.dark:root`. The device theme is followed with `"userInterfaceStyle": "automatic"` in `app.json`. **Dark mode no**: only `:root`, `"light"`, no `.dark:root`. The brand color from the interview goes into `--primary` (neutral when the user defers the design); `tools/brand-tokens.mjs` prints oklch, so for a color convert it to the HSL triplet the tokens use.
8. **Atoms** are written by hand in react-native-reusables' shape (`class-variance-authority`, `clsx`, `tailwind-merge`, a helper named `mergeClassNames` in `shared/utils/merge-class-names.ts`), one component per kebab-case folder with `index.tsx`: `button` (`min-h-11`, 44 px touch target, `accessibilityRole="button"` and label) and `text`. The reusables CLI is interactive and brings `@rn-primitives/*`; use it only when the project needs a component built on those primitives.
9. **Routes**: `app/_layout.tsx` imports `../global.css`, renders `<StatusBar style="auto" />` and a `Stack` with `headerShown: false`; one thin file per route that re-exports a page (`export default Home;`). `app/` is the only place with default exports (a route requires one) and `_layout.tsx` the only file that is not kebab-case.
10. **State and storage**: Zustand with the `persist` middleware over `createJSONStorage(() => mmkvStorage)`; `shared/storage/mmkv-storage.ts` adapts `createMMKV` (`getString`, `set`, `remove`) to Zustand's `StateStorage`. Money is kept in cents and formatted with `Intl.NumberFormat` in `shared/utils`.
11. **Forms**: React Hook Form, Zod and `@hookform/resolvers` (latest releases that pass strict peers; Zod 4 and resolvers 6 worked). The schema is hand-written in the page's `schemas/` folder (there is no generated one without a backend) with the inferred type in `types/`; the page hook owns `useForm({ resolver: zodResolver(schema) })`, `handleSubmit` and navigation, and returns `control`, the error message and `onSubmitPress`; a field molecule wraps `Controller` and takes `control` as a prop, with `handle…` names for the render callbacks (`react/jsx-handler-names`). Form libraries added 0.9 MB to the empty app's bundle (3.57 to 4.43 MB).
12. **Native modules** that need a permission declare it in the `plugins` of `app.json` (`expo-camera` with `cameraPermission` text in the product language and `recordAudioAndroid: false`). They need a development build: MMKV and the camera pipeline rule Expo Go out.
13. **Tests**: `jest.config.js` with two projects, `unit` (`*.spec.ts`) and `integration` (`*.spec.tsx`), preset `jest-expo`, `moduleNameMapper` for the aliases, a `src/test/setup.ts` that mocks `react-native-mmkv` in memory; coverage thresholds 80% for lines, statements, functions and branches over `src`, excluding `components/atoms`, `types/` folders, `src/test` and specs (the `app/` routes are outside `src`: thin files with no logic). Mocks only at the edges: native modules and `expo-router`; a mock factory may name a component in PascalCase. Queries by role and text (`getByRole('button', { name })`), never by class.
14. **Lint**: `eslint.config.mjs` flat config with typed linting (`projectService`), `strictTypeChecked`, React, hooks and `eslint-plugin-react-native-a11y` (`configs.basic.rules` with `has-accessibility-hint` off, which demands a hint on every touchable), `react/no-multi-comp`, no default exports (off in `app/**`), `simple-import-sort`, `check-file` naming (off for `app/_layout.tsx`; `hooks/*.ts` camelCase), `id-denylist`, `naming-convention`, `no-magic-numbers` (off in specs, atoms and `shared/constants`), the size and complexity limits of `recipes/coding-standards.md`, the type selectors that keep types in `types/` folders and `max-statements` 5 on non-spec `.tsx` files. Config files, `scripts/` and `.claude` are ignored. **`prettier --check .` also checks Markdown, JSON and YAML**: run `project format` after writing the docs, the README and the VS Code files, or the first commit is rejected. `prettier-plugin-tailwindcss` takes `tailwindConfig` (Tailwind 3 has no `tailwindStylesheet`). `jscpd` reads `.jscpd.json` (specs and atoms ignored). Two rules of `recipes/coding-standards.md` have no tool here and are left to `/code-review`: boolean flag parameters and the five-props limit.
15. **Architecture**: `.dependency-cruiser.cjs` with the five rules of `recipes/frontend/architecture.md` (components never reach `state/` or `pages/`; only `pages/*/hooks/` use `state/`; `shared/` imports nothing of the app; `state/` imports only `shared/`), no cycles and no barrel (`index.ts`), each rule with its `comment`; `tsConfig` set so the aliases resolve; specs and `src/test` excluded. A rule's `from.path` that must exempt `hooks/` uses a negative look-ahead (`^src/pages/(?![^/]+/hooks/)`).
16. **Dependency audit**: `scripts/audit.mjs` over `pnpm audit --json` with `audit-allowlist.json` (id, package, reason, expiry date). Expo's own CLI (`@expo/cli`) brings advisories with no fix (`node-forge`, `zod`); they are development tools that never ship in the app, so they are allowed with that reason and a 30-day expiry, renewed or removed by a ticket.
17. **Bundle size**: `scripts/check-size.mjs` runs `expo export --platform android --output-dir dist`, sums the `.hbc` files, deletes `dist` and fails above the limit (5 MB; the empty app measured 3.57 MB). This is the mobile counterpart of the web gate; the 10%-growth warning of `recipes/mobile/architecture.md` needs the previous build and is added with the release workflows.
18. **`project` script** (`recipes/dev-commands.md`): POSIX `sh`, no Docker (a mobile app runs on the host); each command maps to the `package.json` script of the same name and `project check` runs `lint typecheck arch coverage audit size` one after another. `openapi` and `openapi:check` print that they do not apply and exit `0` while there is no backend. `setup` runs `pnpm install --frozen-lockfile` and `pnpm exec lefthook install`. Arguments are passed as `pnpm run <script> "$@"` (a `--` before them reaches `tsc` as an unknown option).
19. **Lefthook** as an exact `devDependency` (`recipes/agent-rules.md`, Lefthook): pre-commit `./project lint` and `./project typecheck`, pre-push `./project test:unit` and `./project arch`.
20. **CI**: `.github/workflows/ci.yml` with jobs named `ci / pr-rules` and `ci / gates` so the branch protection of `recipes/github-setup.md` is the same as for the other repositories. It is **standalone, not a caller of the Shared Workflow `project-ci`**, whose last step builds a Docker `prod` target a mobile app does not have; the jobs run `./project setup` and each gate. Use the latest major of `actions/checkout`, `actions/setup-node` and `pnpm/action-setup` (`node-version-file: .nvmrc`, pnpm read from `packageManager`) and prove the file with `actionlint` (`docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest`). No `deploy.yml`: the store workflows need the user's accounts.
21. **Strip comments**: the skeleton ships none worth keeping; the only comments left are the `comment` fields of the dependency-cruiser rules.
22. **The interview's answers** reach the app like this: the project name gives the repository `<slug>-mobile` and `slug` in `app.json`; the product name goes in `app.json` `name`, the home title and the README; the product language sets the texts the shopper sees (written in components and hooks while there is a single language; an i18n library is added when a second language is asked for); the bundle identifier and the Android package are a placeholder (`dev.<owner>.<slug>`) the user confirms when creating the store apps.

## Prove it

- Run each gate alone (`project lint`, `typecheck`, `arch`, `coverage`, `audit`, `size`), then `project check`.
- Break one thing on purpose per gate and see it fail: a component importing `@state/…` (`arch`), an `any` (`lint`), a threshold above the real coverage (`coverage`), an invalid assignment (`typecheck`), an expired allowlist date (`audit`). Undo each.
- Commit a file with a lint error and check Lefthook rejects the commit, then commit the fixed state and run `pnpm exec lefthook run pre-push`.
- Pipe the guardrail cases of `recipes/agent-rules.md` into `.claude/hooks/guardrails.sh` (26 blocked, 8 allowed on the Somaí run).
- Open the app on a device through a development build: manual, by the user.

## Dev commands

The `project` script maps each command to the `package.json` script of the same name (`recipes/dev-commands.md`); `start:dev` is `expo start`, `test:unit` and `test:integration` are the two Jest projects, `audit` is `node scripts/audit.mjs` and `size` is `node scripts/check-size.mjs`.
