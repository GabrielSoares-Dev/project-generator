# Mobile architecture

The mobile app Stack Recipe (ADR-0012). Built from the user's `Boilerplate-react-native-expo`, updated to the decisions recorded here.

## Platform

- **TypeScript**, strict, the same configuration as the web frontend; no JavaScript files in `src/` or `app/`.
- **Versions**: the latest Expo SDK and the React Native version it ships, Node LTS, following the version policy in `recipes/decision-guide.md`.
- **Expo only**, with a development build and `expo prebuild` when a native module is needed. The `android/` and `ios/` folders are never committed, so the agent never edits native code, and EAS handles builds, store submission and updates. No bare React Native variant.

## Styling

**NativeWind** (Tailwind for React Native) with **react-native-reusables** (shadcn/ui for React Native), generated into `components/atoms/` like the web design systems. The Brand Tokens live in the Tailwind theme, so the app shares the web's styling language; no hardcoded colors in components.

## Libraries and conventions

- **Same as React web where they apply** (`recipes/frontend/libraries.md`): TanStack Query (hooks generated by orval), zustand, axios with an interceptor that sends `Authorization: Bearer` and refreshes the token on 401 (ADR-0009), react-hook-form, generated Zod schemas, toasts.
- **Storage**: tokens only in **Expo SecureStore** (Keychain / Keystore); **MMKV** for non-sensitive persisted state.
- **Conventions identical to the web frontend** (`recipes/frontend/architecture.md`, `recipes/coding-standards.md`): one `.prettierrc` with semicolons, PascalCase component folders, co-located `.spec` tests, no aggregated barrels, strict TypeScript and ESLint **with the React hooks rules on**, user-facing text in the product's language, Problem Details handling, component shape rules.
- **Accessibility gate**, with mobile tools: `eslint-plugin-react-native-a11y` in lint (missing `accessibilityLabel`, small touch targets…) and React Native Testing Library accessibility queries in component tests.
- **Coverage ≥ 80%**, excluding the design-system components generated into `components/atoms/` and configuration, like the web.
- **Tests**: Jest with the `jest-expo` preset, React Native Testing Library and MSW in the agent's session; **Maestro** end-to-end tests in CI (Android on every pull request, iOS on demand).

## Release and updates

- **EAS Update** is on: JavaScript-only changes reach users without a store release, guarded by Expo's `runtimeVersion` policy so an update never lands on an incompatible installed binary.
- **Pipelines publish to the stores** (EAS Build + EAS Submit), never a manual upload. A release goes first to **internal testing** (TestFlight on iOS, the internal track on Google Play), where the human installs and checks the final store build; a second manual workflow then **promotes** it to production (Apple review and Google Play production).
- **Three manual workflows**:
  - `release-store`: EAS Build + EAS Submit to TestFlight and the internal track, with the version set in the release pull request;
  - `promote-store`: promotes that build to production in both stores;
  - `update-ota`: publishes a JavaScript-only fix through EAS Update on the production channel, no store involved.
- Store credentials (App Store Connect API key, Google Play service account) are kept in EAS; GitHub holds only the `EXPO_TOKEN` secret.
- **Versions**: the build number is incremented by EAS (`autoIncrement`, as in the user's boilerplate); the visible version (`1.4.0`) is set by the human in the release pull request.
- **App size** is recorded on every production build, and a warning (not a block) is raised when it grows more than 10% from the previous build, the mobile counterpart of the web bundle-size gate.
- **Local Review reaches the local backend**: the development build points at the developer machine's LAN IP (`EXPO_PUBLIC_API_URL=http://192.168.x.x:8080`), set automatically by `pnpm dev:lan`; off the local network, a tunnel (`expo start --tunnel` or ngrok). Code under review never talks to production.
- **Production channel only**, following the single-environment rule; Local Review uses the development build on the user's phone.

## Errors and notifications

- JavaScript errors go to the backend's `POST /v1/client-errors`, like the web. Known limitation: native crashes (outside JavaScript) are not captured this way.
- **Offline**: by default the app shows the last TanStack Query cached data and the error state when there is no network. True offline support (queuing actions and syncing later) is an on-demand mechanism, chosen through the decision guide.
- Push notifications are an on-demand mechanism (Expo Notifications), chosen through the decision guide.

## Structure

The **same architecture as the web frontend** (`recipes/frontend/architecture.md`): Atomic Design in `components/`, plus `pages/`, `state/`, `services/` (generated by orval) and `shared/`, with the same five rules checked by dependency-cruiser. Expo Router's `app/` folder holds **only thin route files** that render pages, grouped as `(public)` and `(private)`, each group's `_layout.tsx` wrapped in its guard (as in the user's boilerplate).

```
app/
├── (public)/_layout.tsx, login.tsx      thin routes → pages/
└── (private)/_layout.tsx, home.tsx
src/
├── components/{atoms,molecules,organisms,templates}/
├── pages/
├── services/<feature>/                  generated by orval
├── state/<feature>/
└── shared/{http,utils,types,constants,hooks}/
```
