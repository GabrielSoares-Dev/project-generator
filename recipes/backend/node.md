# Node (TypeScript)

The Node backend Stack Recipe. It follows `recipes/backend/clean-architecture.md`, whose **Code rules, Testing rules and Extra mechanisms rules** apply as written; this recipe only says how Node meets them and which tools it uses. The variant is chosen per Derived Project through `recipes/decision-guide.md`. Built from the user's `Boilerplate-nestjs-docker` and `Boilerplate-nestjs-serverless`, updated to the Template's decisions.

## Variants

- **Custom stack (the default)**: **Fastify** plus libraries chosen by the Template, with the clean architecture as the only structure; dependency injection is manual, wired in `infra/composition-root.ts`. Emphasized because NestJS tends to over-engineer: its modules, decorators and DI would be a second structure competing with the clean architecture. Fastify is mature and fast, and its **Zod schemas** validate requests and generate the OpenAPI spec straight from code (ADR-0008), with the same Zod the frontend uses. Hono is the alternative only when the smallest possible Lambda cold start is the priority.
- **NestJS**: only when the team maintaining the project already works with Nest, or a client requires it. The clean architecture stays inside; Nest lives only in `infra` (controllers, modules, providers). Use cases stay plain classes, registered as providers from `infra`.
- **Plain Node**: only for small Event Functions, no HTTP and no framework, with the full clean-architecture structure (same rule as plain Java and plain PHP).

## Status

The **custom stack** variant (Fastify, Drizzle, PostgreSQL) is generatable end to end for the **VPS container** target (`recipes/vps-deploy.md`, ADR-0013): *Generating the project* below was proven by generating a backend, passing every gate and running its `prod` image (run of 2026-11-16, `.scratch/node-backend/`). Not generated yet, and so not offered by `/new-project`: the **NestJS** and **plain Node** variants, and the **AWS Lambda** runtime (`serverless.yml`, `LambdaHandler.ts`) described under *Runtime*, which stays the design until a project needs it. Extra mechanisms (queue, files, email, cache) are not generated.

## Versions

Node is the latest LTS the chosen libraries support; TypeScript and every library the latest stable, following the version policy in `recipes/decision-guide.md`; pinned through `.nvmrc`, `engines`, `packageManager` and the lockfile.

## Structure and names

- Folders are those of `recipes/backend/clean-architecture.md` (`src/domain`, `src/application/useCases/<feature>`, `src/application/dtos/<…>/<action>`, `src/infra/…`), with path aliases `@domain/*`, `@application/*`, `@infra/*` (as in the boilerplate).
- **File names follow the other backend recipes**: one exported class or type per file, and the **file name is the class name** in PascalCase, as Java and PHP (PSR-4) require: `application/useCases/role/CreateRoleUseCase.ts`, `application/repositories/RoleRepositoryInterface.ts`, `application/dtos/useCases/role/create/CreateRoleUseCaseInputDto.ts`, `infra/repositories/role/RoleRepository.ts`. This replaces the boilerplate's camelCase, entity-less names (`create.usecase.ts`).
- Corrections applied to the boilerplate: `execute` instead of `run`; Problem Details from one global error handler instead of the `{ statusCode, message, content }` envelope and per-controller `try/catch` on message strings; `BusinessException(ErrorCode)` in `domain` (the boilerplate's domain imported it from `application`); UUID v7; authentication only (no `@Permission` / RBAC); `httpOnly` cookies for the web; `Start` / `Finish` flow logs at `debug`.

## How Node meets the general rules

- **Framework-free inner layers**: no Fastify, Nest, Drizzle or SDK imports in `domain` or `application` (dependency-cruiser); dependencies arrive through the constructor (`constructor(private readonly roleRepository: RoleRepositoryInterface)`), wired in the composition root (or as Nest providers in the Nest variant).
- **Transactions**: Drizzle's `db.transaction(...)`, only inside repositories.
- **Types**: dates are `Date` in UTC (ISO strings at the API edge); money is integer cents in a `Money` value object, never a floating-point `number`; enumerations as `as const` objects with a derived union type (`ErrorCode` included); lookups return `T | undefined`, never `null` sentinels; collections returned as `readonly T[]`.
- **DTOs and value objects** are classes with `readonly` properties; mapping is hand-written (`fromModel` / `toDto` functions); repositories never return Drizzle rows.
- **Tests**: Vitest mocks (`vi.fn()`) for ports only, builders in `tests/helpers/builders`, the database reset between integration tests.
- **Mechanisms**: in-process schedulers (`node-cron`, `@nestjs/schedule`, `setInterval` jobs) are forbidden; consumers are push (an Event Function per queue on Lambda, a push endpoint for Pub/Sub).

## ORM: Drizzle (both variants)

Replaces the boilerplate's Prisma. SQL-like typed queries; raw SQL through ``sql`...` `` with escaped parameters; schema in TypeScript, with `drizzle-kit generate` producing plain, editable SQL migrations; types straight from the schema (no generate step); no binary engine, which keeps Lambda cold starts low. PostgreSQL and MySQL. Drizzle tables and types stay in `infra/models`.

## Tests and quality

- **Vitest** (replaces the boilerplate's Jest, same runner as the frontend); integration tests with `fastify.inject` (Supertest on NestJS) against the real database of the Compose `db` service, in its own `app_test` database (ADR-0003), like the other recipes. Testcontainers is not used: it needs the Docker socket inside the dev container and inside CI's `docker compose run` (the same reason as in `recipes/backend/go.md`).
- **Strict ESLint** with `@typescript-eslint/no-explicit-any` on, and the **same `.prettierrc` as the frontend**.
- **Strict `tsconfig`** (`strict`, `noImplicitAny`, `strictNullChecks`, `noUncheckedIndexedAccess`…), fixing the boilerplate's loose settings.
- **dependency-cruiser** for architecture validation, **jscpd** for duplication, ESLint complexity rules for the limits of `CODING_STANDARDS.md`.
- **80% coverage** on `domain` + `application`.

## Conventions enforced by tools

- **Format**: Prettier (CI checks, pre-commit applies).
- **Architecture and naming** (dependency-cruiser + eslint-plugin-check-file + custom ESLint rules): file name equals the exported class; classes in `application/useCases` end in `UseCase` and expose a single public method, `execute`, declared last; ports in `application/repositories` and `application/services` are interfaces ending in `Interface`; DTOs end in `Dto`; controllers end in `Controller`.
- **ESLint**: no `console.*` outside the logger, no floating promises, no `any`, no non-null assertions.

## Runtime

- **AWS Lambda**: packaged and deployed with the **Serverless Framework**, which manages the Lambda functions and API Gateway; everything else (database, buckets, CDN, alerts, budget, `-dev` resources) stays in Terraform, linked through SSM parameters (exception in ADR-0002). The HTTP API enters through one file, `infra/functions/api/LambdaHandler.ts`, wrapping the Fastify app with `@fastify/aws-lambda` (exception in ADR-0002). Code is **bundled with esbuild** (`serverless-esbuild`): minified, tree-shaken, packaged per function, with the AWS SDK v3 left out because the Lambda runtime provides it, so packages stay small and cold starts low. Deploys run only in the pipeline, via OIDC.
- **Containers** (Cloud Run, ECS): the same Fastify app, no adapter, from the `Dockerfile` `prod` target: the esbuild bundle on a Node slim / distroless base, non-root. The `dev` target carries Node, pnpm and the quality tools with hot reload.

## Implementation notes

- `LoggerService` on **pino** (JSON); the request ID travels through `AsyncLocalStorage` onto every log line.
- Configuration comes from environment variables, validated with Zod at startup; no per-environment files holding secrets.
- Validation messages shown to end users are in the product's language; everything technical stays in English.
- Graceful shutdown: Fastify's `close()` on `SIGTERM`, with a timeout below the cloud's grace period.

## Generating the project

Learned from generating a Node backend end to end (run of 2026-11-16, `.scratch/node-backend/issues/01-generate-node-backend.md`). The custom stack has no skeleton to create and clean up: every file is written, so there is nothing to strip. Follow in this order:

1. **Tooling in the container, so the host needs only Docker.** The `dev` image is `node:<node major>-bookworm` from Docker Hub (the latest LTS the libraries support; Node 26 on 2026-11-16). **Images from Node 25 on carry no Corepack** (`corepack: not found`), so the `dev` stage installs pnpm itself: `npm install --global pnpm@<version>` (the frontend recipe's Corepack line holds only up to Node 24). Pin Node in `.nvmrc`, `engines` and the Dockerfile, pnpm in `packageManager`.
2. **Check peer dependencies before settling on versions** (as `recipes/frontend/react.md`, item 2). On 2026-11-16: `typescript-eslint` accepts TypeScript below 6.1 while `latest` was 7.0, so TypeScript stays on 6.0; `fastify-type-provider-zod` needs Zod 4.1.5 or newer and `@fastify/swagger`; `@types/node` is the Node LTS's. `pnpm-workspace.yaml` holds `strictPeerDependencies: true` and `allowBuilds` (`esbuild: true`, `lefthook: true`); `savePrefix` is not honoured, so strip the `^` from `package.json` after the installs (the lockfile has the resolved versions). Run every install in the container (`docker compose run --rm app pnpm add …`): a `node_modules` created on the host would mix with the container's.
3. **TypeScript** (`tsconfig.json`, no `baseUrl`, `noEmit`): `module` `ESNext`, `moduleResolution` `Bundler`, `target` `ES2024`, `types` `["node", "vitest/globals"]`, every strict flag of *Tests and quality* plus `exactOptionalPropertyTypes`, `noImplicitOverride`, `noImplicitReturns`, `verbatimModuleSyntax` and `isolatedModules`; `paths` `@domain/*`, `@application/*`, `@infra/*` and `@tests/*`, each starting with `./`. `package.json` has `"type": "module"`. tsx, esbuild and Vitest (`resolve.tsconfigPaths: true`) all read the same `paths`, so no alias is repeated.
4. **Dockerfile, four stages** (item 17 has the Compose files):
   - `dev`: the Node image, pnpm (item 1), `git config --system --add safe.directory /app` (the bind-mounted repository belongs to another user and Git refuses it otherwise, so hooks and commits made inside the container fail), `/app/node_modules` created and owned by `node` (a new named volume inherits that ownership), `USER node`, `ENV CHOKIDAR_USEPOLLING=true` (inotify events do not cross a Windows or macOS bind mount, and `tsx watch` honours this variable), `HEALTHCHECK NONE`, `CMD ["sleep", "infinity"]`;
   - `runtime`: `node:<major>-alpine`, with `/usr/local/lib/node_modules`, `/usr/local/include`, `/usr/local/share`, `npm`, `npx`, `corepack`, `/opt` (yarn) removed in the same layer;
   - `build`: `node:<major>-alpine`, pnpm, `pnpm install --frozen-lockfile --ignore-scripts` over `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml` (a cached layer), then `tsconfig.json`, `scripts/` and `src/`, then `pnpm run build`;
   - `prod`: **`FROM scratch`**, `COPY --from=runtime / /` (the flattening that `recipes/vps-deploy.md` explains), `ARG APP_VERSION=dev`, `ENV NODE_ENV=production APP_ENV=production APP_VERSION=${APP_VERSION} MIGRATIONS_FOLDER=/app/migrations`, `COPY --from=build --chown=node:node /app/dist /app`, `USER node`, `HEALTHCHECK CMD ["node", "/app/main.mjs", "healthcheck"]` (no `curl` in the image), `ENTRYPOINT ["node", "/app/main.mjs"]`, `CMD ["serve"]`. **223 MB measured** (the Alpine Node image alone is 252 MB; the Node binary is most of it), under the 250 MB target of `recipes/vps-deploy.md`.
5. **The build** is `scripts/build.mjs`: esbuild bundles `src/main.ts` into `dist/main.mjs` (`platform: 'node'`, `format: 'esm'`, `target: 'node<major>'`, minified, no source map, a `createRequire` banner for the CommonJS packages the bundle pulls in), then copies `src/infra/database/migrations` to `dist/migrations`. `pnpm run build` is the only build command.
6. **One entry point, several commands** (`src/main.ts` parses `Config` from `process.env` and hands the command to `infra/config/CommandRunner`): `serve` (the default: builds the application, runs the migrations, listens on `HTTP_PORT`, and on `SIGTERM` or `SIGINT` closes the server and the pool within `SHUTDOWN_GRACE_PERIOD_MS`, exiting 0), `serve:no-migrate` (a second process of the same image), `migrate`, `migrate:fresh` (drops the `public` and `drizzle` schemas and migrates; refuses unless `APP_ENV=local`), `seed` (prints that there is no development data yet, until a feature adds entities), `healthcheck` (a `fetch` of `http://127.0.0.1:<port>/health` with a 3-second timeout) and `openapi` (prints the specification). `main.ts` is the only file that may break the one-export rule (it exports nothing).
7. **Composition** (manual, no container library):
   - `infra/config/Config.ts` exports the Zod schema and, with the same name, its inferred type (`export const Config = z.object({...})`, `export type Config = z.infer<typeof Config>`): `APP_ENV` (`local`, `test`, `production`), `APP_VERSION`, `HTTP_PORT`, `LOG_LEVEL`, `CORS_ALLOWED_ORIGINS`, `MIGRATIONS_FOLDER` (default `src/infra/database/migrations`), `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_CONNECT_TIMEOUT_MS` (default 3000), `SHUTDOWN_GRACE_PERIOD_MS`, `CLIENT_ERROR_RATE_MAX` and `CLIENT_ERROR_RATE_WINDOW_MS`; numbers use `z.coerce`, and a missing database variable stops the start with Zod's message;
   - `infra/database/Database.ts` wraps one `pg` `Pool` (`connectionTimeoutMillis` and `statement_timeout` from `DB_CONNECT_TIMEOUT_MS`, an `error` listener so an idle-client error never crashes the process), exposes `client` (Drizzle on `node-postgres`), `migrate(folder)` and `close()`;
   - `infra/config/CompositionRoot.ts` builds the `Database`, the `LoggerService`, the repositories, the use cases and the controllers, and exposes `controllers: ControllerInterface[]`; a new feature adds its objects here and one entry to the list;
   - `infra/config/Application.ts` creates the Fastify instance and its `build()` registers, in order, the Zod compilers, the request ID, the plugins, the error handlers and the controllers, then `await server.ready()`; the integration tests call the same class.
8. **Request ID**: Fastify's `requestIdHeader` is `x-request-id` and `genReqId` is `RequestIdFilter.resolve` (the incoming value up to 128 characters, else a UUID v7), so `request.id` is the trace ID; an `onRequest` hook writes it into the response header and runs the rest of the request inside `RequestContext.run({ requestId }, done)` (`AsyncLocalStorage`), which the logger's `mixin` reads for every line.
9. **Problem Details** (ADR-0011): `ErrorCodeDetails` maps each `ErrorCode` to its HTTP status, `title` and `detail` (the texts in the product language), `ProblemDetailsFactory.create(errorCode, traceId, errors?)` builds the body, and `ErrorHandler` is the one global handler (`setErrorHandler`) and the not-found handler: a `BusinessException` maps to its code, a Zod validation failure (`hasZodFastifySchemaValidationErrors`) to `VALIDATION_FAILED` with `errors` holding `field` (the `instancePath` without the leading slash, `/` turned into `.`) and `message`, a rate-limit error (`statusCode` 429) to `TOO_MANY_REQUESTS`, anything else to `INTERNAL_ERROR` logged at `error`; an unknown route is `RESOURCE_NOT_FOUND`. The content type is `application/problem+json`, and the body carries `type` (`about:blank`), `title`, `status`, `detail`, `code`, `traceId` and `errors` only for validation. The use case throws `BusinessException(ErrorCode.DatabaseUnavailable)` and the handler turns it into the 503.
10. **Routes and the contract**: each controller is a class implementing `ControllerInterface` (`register(app: FastifyInstance)`) whose routes use `app.withTypeProvider<ZodTypeProvider>()`, with `operationId` (`healthShow`, `clientErrorsCreate`: `<resource><Action>`, which orval turns into the frontend's function names), `summary` and a `response` schema per status, **including the Problem Details statuses**; the request and response schemas are `infra/http/validators/<feature>/<Name>Validator.ts` (a Zod object, one per file). `@fastify/swagger` takes `openapi: '3.1.0'`, `info.title` the product name, a fixed contract `version` `1.0.0` and the local server URL (the host port); `transform: jsonSchemaTransform`. Two problems of the Zod provider are fixed by one class, `infra/config/OpenApiTransform.ts`, passed as `transformObject` (it calls `jsonSchemaTransformObject` first): a schema registered with `.meta({ id })` is emitted twice, as `ProblemDetails` and `ProblemDetailsInput`, so the unused `…Input` variant is dropped (otherwise the frontend's client gets a type nobody uses), and a `204` response keeps no `content` (`response: { 204: z.void() }` generates an empty JSON body). `ProblemDetailsValidator` registers itself with `.meta({ id: 'ProblemDetails' })`, with `status` bounded to 100 to 599 (a plain `.int()` writes the 53-bit limits into the contract). `openapi.json` is committed; `pnpm run openapi` writes it and `pnpm run openapi:check` (`scripts/check-openapi.mjs`) regenerates it in memory and fails with `openapi.json is out of date: run ./project openapi`.
11. **CORS** with `@fastify/cors`: the origins split from `CORS_ALLOWED_ORIGINS`, `credentials: true`, `exposedHeaders` the request ID header, `allowedHeaders` `content-type`, `x-requested-with`, `accept-language`, `x-timezone` and the request ID header. An unknown origin gets no `access-control-allow-origin` at all (the test asserts it).
12. **`POST /v1/client-errors`** (`recipes/backend/clean-architecture.md`, Observability; the React frontend calls it from its global error listeners): `LogClientErrorUseCase` logs `client error` at `error` with `message`, `stack` and `url`; `LogClientErrorValidator` is `message` 1 to 1000 characters, `stack` up to 8000 and `url` up to 2000 (both optional); the route answers 204 and is rate-limited by `@fastify/rate-limit` registered with `global: false` and a per-route `config: { rateLimit: { max, timeWindow } }` taken from `CLIENT_ERROR_RATE_MAX` and `CLIENT_ERROR_RATE_WINDOW_MS`. Integration tests: 204, 422 without `message`, 422 above 1000 characters, 429 on the fourth call with a maximum of 3.
13. **Logging**: `LoggerService` on pino (`base: null`, ISO timestamps, `level` as a label, JSON on stdout or on the destination the test passes), the request ID from `RequestContext` in a `mixin`, the fields under `context` with the sensitive names (`password`, `token`, `secret`, `authorization`, `cookie`, `cpf`, `cardnumber`, compared in lowercase) replaced by `***` at every nesting level and in arrays, and an `Error` logged as `name`, `message` and `stack`. The logger is constructed with its level and an optional destination, so a test captures the lines.
14. **Database**: tables live in `src/infra/models/<Name>Model.ts` (Drizzle `pgTable`, `casing: 'snake_case'` in `drizzle.config.ts`: code in camelCase, columns in snake_case). `drizzle-kit generate` writes plain SQL migrations into `src/infra/database/migrations` as `0000_<name>.sql` plus the `meta/` journal (drizzle-kit's naming replaces `V<n>__<description>` of the shared layout); `serve` and `migrate` apply them through Drizzle's `migrate()` from `MIGRATIONS_FOLDER`. A fresh project has no table, so the first migration is a **custom** one that sets the database timezone to UTC: `drizzle-kit generate --custom --name=set_database_timezone_utc`, whose body is a `DO` block running `ALTER DATABASE %I SET timezone TO 'UTC'` over `format('%I', current_database())`. `drizzle-kit` refuses to run when the schema folder has no file, so create a temporary `src/infra/models/placeholder.ts` containing `export {}`, run the command and delete the file. `HealthRepository.isDatabaseReachable` runs `SELECT 1` and returns `false` on any error, so the use case, not the repository, decides what unreachable means.
15. **Tests**: Vitest 5 with two projects, `unit` (`tests/unit/**/*.spec.ts`) and `integration` (`tests/integration/**/*.spec.ts`, `fileParallelism: false`, `hookTimeout` 30000, a `globalSetup` that migrates `app_test`), run with `--project`; `globals: true`; `test.env` holds the test configuration (`APP_ENV=test`, `APP_VERSION=test-version`, `DB_DATABASE=app_test`, `LOG_LEVEL=error`, a rate limit of 3 per 60 s), with the other database variables read from the environment. Layout and names follow `recipes/backend/clean-architecture.md`: `tests/unit/{domain,application,infra}/…/<ClassName>.spec.ts`, `tests/integration/http/<feature>Controller/<Feature>Integration.spec.ts`, helpers in `tests/helpers`: `TestApplication` (`start(overrides)` builds the real application with a `Writable` as the log destination and exposes `server`, `logLines`, `resetDatabase()` which truncates every table of the `public` schema and `stop()`) and `builders/` (a factory function per builder, `aLogClientErrorInput().withMessage('boom').build()`). The integration tests cover `/health` up and down (503 `DATABASE_UNAVAILABLE` with the `traceId` from the request header, started with `DB_HOST=127.0.0.1` and `DB_PORT=1`), an unknown route, CORS (allowed origin, preflight, unknown origin) and the client errors. **Coverage** is `vitest run --project unit --coverage` with `provider: 'v8'`, `include` `src/domain/**` and `src/application/**`, and 80% thresholds for lines, statements, functions and branches.
16. **Lint and format**:
    - `.prettierrc` is the frontend's (`recipes/frontend/architecture.md`), with `.editorconfig`; Prettier also checks the YAML and JSON of the repository, so run `project format` before the first `project lint`; `.prettierignore` holds `openapi.json`, the lockfile, `build`, `dist`, the migrations' `meta/` and the agent team's rendered folders;
    - `eslint.config.mjs` is a flat config on `typescript-eslint`'s `strictTypeChecked` and `stylisticTypeChecked` with `projectService`: `no-explicit-any`, `no-non-null-assertion`, `no-floating-promises`, `explicit-member-accessibility`, `explicit-function-return-type`, `consistent-type-imports`, `member-ordering` (`constructor`, `private-method`, `public-method`: the public methods come last, so `execute` does), `no-console`, `complexity` 10, `max-lines-per-function` 30, `max-params` 4, `max-depth` 3, `max-lines` 300, `id-denylist` for the names of `recipes/coding-standards.md`, `no-extraneous-class` with `allowStaticOnly` (the static factories), `simple-import-sort` with groups `node:`, packages, the four aliases, relative (without a group for the aliases, the sorter treats `@infra/…` as a scoped package and puts it among the libraries);
    - names by `eslint-plugin-check-file`: files PascalCase and folders camelCase under `src` and `tests`, `index.ts` blocked (no barrels), `*UseCase` under `application/useCases`; the builders folder is camelCase;
    - one local rule, `eslint-rules/file-name-matches-export.mjs`: a file under `src` exports exactly one name and it is the file's name (a Zod object and its inferred type may share the name); `src/main.ts`, which exports nothing, is outside it;
    - use cases: `no-restricted-syntax` on `MethodDefinition[kind='method'][accessibility='public']:not([key.name='execute'])`, so a second public method fails;
    - the config files (`*.mjs`, `*.cjs`, the root `*.ts`) use `typescript-eslint`'s `disableTypeChecked`, **merged** into one block (`languageOptions` and `rules` spread from it): a block that spreads it and then writes its own `languageOptions` replaces the `projectService: false` and the files fail with "not found by the project service";
    - `.jscpd.json`: `minTokens` 50 over `src` and `tests`, migrations ignored, `threshold` 0.
17. **Architecture** with dependency-cruiser (`.dependency-cruiser.mjs`, `export default`; run `depcruise src tests`): `domain` imports only `domain`; `application` imports only `domain` and `application`; neither imports a library or a Node module (dependency types `npm`, `npm-dev`, `npm-peer`, `npm-optional`, `core`); `src` never imports `tests`; no cycles; no `index.ts`. **Do not set `includeOnly`**: it drops the library edges from the graph before the rules look at them, and a `fastify` import in `domain` passed the gate (found by the proof of item 22); keep `doNotFollow: { path: 'node_modules' }` and `tsConfig` so the aliases resolve.
18. **Docker Compose for development** (`docker-compose.yml`): `app` (target `dev`, `.env` as an optional `env_file` (`required: false`), the host port of the interview mapped to 8080, the repository at `/app`, named volumes for `/app/node_modules` and pnpm's store) with `depends_on: db: condition: service_healthy`, and `db` (`postgres:<version>-alpine`, the volume at `/var/lib/postgresql`, `docker/postgres/init.sql` creating `app_test`, a `pg_isready` health check). **No `container_name` in this file**: the production file names its `app` container, and two files naming the same container fail to run side by side (the `db` of the first run clashed). `docker-compose.prod.yml` as in `recipes/vps-deploy.md`, `app` named `<slug>-backend`, the health check `["CMD", "node", "/app/main.mjs", "healthcheck"]`, `db` without a `container_name` and with `$$POSTGRES_USER` and `$$POSTGRES_DB` read from `stack.env`; `stack.env.example` lists every variable with `change-me` placeholders, the `POSTGRES_*` ones and the real origin of the frontend; `.env.example` is the local file `project setup` copies (`DB_HOST=db`, `DB_PASSWORD=secret`).
